D7 追加：§12.7 I-10 附件状态机、配额与优先回收落地（分支 `feature/attachment-status-quota`）。`ai_message_attachment` 补 `status` / `expire_at` 两列（双方言同存；门禁禁 `alter`，新列只能写在 `create table` 行内），四态按 §12.6 原口径跑通：登记即 `PENDING` + `expire_at = 上传 + pending-attachment-ttl-hours`；随消息发送转 `BOUND`（脱离配额，`expire_at` 只作展示）；会话删除 / 整轮删除把在架附件转 `ORPHANED` + `expire_at = 转孤立 + orphan-attachment-ttl-hours` 的留档宽限；到期后 `PENDING` **连行删掉**（没有消息引用它，留一行只会永久占着配额账目）、`ORPHANED` 只转 `RECYCLED` 留元数据行给审计。四件事值得记：

1. **一轮里两遍扫描的顺序是契约，不是实现细节**。回收每 1h 一轮，先收到期 `PENDING` 再收到期 `ORPHANED`，两遍都最旧的先收。理由不在"哪批更该早点清"这种直觉上：`PENDING` 占着作者的单用户配额，配额堵住的是"这位用户还能不能上传"，而 `ORPHANED` 只是桶里的文件晚一点释放——所以占额度的一方先出血。同理，暂存阈值 `<=0` **只关暂存件那一遍**：会话删完就不再产生新的暂存件，把两遍捆在同一开关上会让已经转孤立的对象永远留在桶里。
2. **配额拦在写库之前，且算"已用 + 本次"**。`PENDING` ≤20 个 / ≤50MB 两条上限各自独立生效，哪个先撞按哪个提示；字节走 `sum(file_size)` 而不是数个数乘平均值，因为一次上传可能就是 40MB 的文档。登录身份取不到时不比对配额——后面的写库同样按登录态鉴权，此处不为拿不到的身份造一条拦截口径。
3. **回收的两种错位都不报错，只会静默毁数据**。扫描丢了 `status` 谓词就把 `BOUND`（正在会话里被查看的）附件文件当到期件删掉，用户看到的是图片打不开；登记丢了 `expire_at` 或回收索引没建，到期件就永远扫不到，附件无声残留到磁盘满。两种都只有接上真实库与桶才暴露，所以这次**门禁 + 单测两层都上**：新脚本 `scripts/checks/attachment-lifecycle-guards.mjs` 管配置与接线面（双方言列与默认值、回收索引、字典齐项、扫描谓词与稳定排序、"先删对象再改库"、周期调度与两个删除调用点、回收接口的权限与 `recycled` 统计），行为面由 `AiAttachmentReclaimerTest`（11 项）、`AiAttachmentReclaimTaskTest`（新，4 项）、`AiChatAttachmentServiceImplTest`（新增 10 项）守住——其中取片 SQL 的 `ORDER BY expire_at ASC,id ASC` 与游标翻页能直接断言，是因为 `AiTestSupport` 为实体注册了 MyBatis-Plus 的 lambda 缓存，captured wrapper 的 `getSqlSegment()` 就是真实下发的那段条件。
4. **新门禁首轮是"假绿"的，变异测试才把它照出来**。方法体截取最初写成"匹配任意 `foo(`"，于是 `reclaim(list)` 这类**调用点**也被当成声明，`bodyFrom` 从那里往后找到的第一个 `{` 往往是 `for` 的括号——五段检查读的全是错位内容，代码怎么改都报绿。修法是把声明锚定到行首的可见性修饰词。同一轮还暴露两处"检查存在但不成立"：只断言 `markOrphaned` 圈了 `PENDING/BOUND`，把 `RECYCLED` 也加进范围照样过关（终态被改回在制品），因此补一条"范围里不得出现 RECYCLED"；只断言 `start()` 里有 `scheduleAtFixedRate`，把调度整体挂在暂存开关上仍然绿，因此补一条"调度入口不得按 TTL 开关短路"。最终 21 项变异全部 rc≠0 且报错命中对应断言，还原后复跑为绿。
